# 紡の設計

★**まだ設計です。実装はありません。** 「実測」と書いたものだけが、手元で確かめた事実です。

## 1. 目的

Claude Code を、**複数の所属**（自社・個人・業務委託先など）ごとに、**無人で常駐**させる。

- Windows / macOS / Linux（Ubuntu）で動く
- OS のサービスとして常駐する（ログインしたら勝手に立ち上がる）
- 仕組みは公開、所属ごとの知識・認証・ルールは手元だけに置く

## 2. 分担

| 層 | 受け持つもの | 在りか |
|---|---|---|
| **Claude Code** | Claude の実行・バックグラウンド起動・セッション間メッセージ | 公式の CLI |
| **紡** | 「どの所属で、どのセッションを、何本」を保つ常駐プロセスと、その決めごと | このリポジトリ |
| **結** | 所属ごとの知識 | 手元の `*.yui`（所属ごとに 1 つ） |
| **手元の設定** | 所属ごとの指示・認証の切り替え | `local/<所属>/`（公開しない） |

紡は **Claude を自分で抱えない。** 抱えるのは Claude Code の `claude daemon` で、紡はそれに
「足りないものを起こし、余計なものを止める」よう指示するだけにする（3 節）。

## 3. 土台にする Claude Code の機能（実測）

2026-11-15、Claude Code 2.1.322〜2.1.323、Linux（WSL2・Ubuntu 26.04）で確かめた。

| やりたいこと | Claude Code の機能 | 実測 |
|---|---|---|
| 端末なしで常駐させる | `claude --bg -n <名前> "<最初の指示>"` | 動く。tmux は要らない |
| 一覧を取る | `claude agents --json`（`name` `kind` `status` `sessionId` `cwd` `pid` `startedAt`） | 動く。`--all` で終わったものも出る |
| 止める・消す・中を見る | `claude stop` / `rm` / `logs` / `attach` / `respawn` | 動く |
| セッション同士で話す | `ListAgents` / `SendMessage`（Claude のツール） | **往復できた**（対話セッション → バックグラウンド → 返信） |
| 終わったら知らせてもらう | `SendMessage` の `notify_when_idle` | 購読できた |

踏んだところ:

- ★**バックグラウンドのセッションは、起動した側の環境変数を受け取らない。**
  受け取るのは、その時点で動いている `claude daemon` の環境変数。
  （1 本目の起動で daemon が立つので、1 本目だけは渡ったように見える。2 本目で別の値を渡すと、1 本目の値が出た）
  ⇒ **所属ごとの環境変数は `--settings '{"env":{...}}'` で渡す。** これはセッションごとに効いた。
  （公式の文書が「起動した側から受け継ぐ」と書いているのは `PATH` やモデルの別名など一部だけ）
- ★**「信頼」していないフォルダでは `--bg` が起動しない**（`Workspace not trusted`）。
  ⇒ 所属の作業フォルダは、登録するときに信頼を済ませておく必要がある。
  公式の文書にある手で済ませる方法は `~/.claude.json` の `projects["<フォルダ>"].hasTrustDialogAccepted` を
  `true` にすること（git の中ならリポジトリの最上位が単位）。★**`--bg` がこれで起動するかは未実測。**
- `claude daemon` は**呼ばれたときだけ立ち、最後の利用者がいなくなると終わる。**
  この版では OS のサービスとしての登録は無効になっている（`claude daemon --help`）。
  ⇒ **ログイン時に立ち上げる役は紡が持つ。**
- 権限モードが違うセッションからのメッセージは、受け手側で人の承認待ちになる。
  ⇒ 1 つの所属の中では権限モードをそろえる。

Windows は、`claude --help` と `claude daemon status` で同じコマンドが在ること
（受け口は名前付きパイプ `\\.\pipe\cc-daemon-*`）までを確かめた。
★**Windows でのバックグラウンド起動とメッセージの往復は未実測。macOS は何も試していない。**

## 4. 所属

所属 = 「誰の仕事として動くか」。例: 自社 / 個人 / 業務委託先 A / 業務委託先 B。

★**所属どうしは混ぜない。** 業務委託先の知識が別の所属のセッションに見えたら事故になる。

| 所属ごとに 1 つ | 例 |
|---|---|
| 手元のフォルダ | `local/<所属>/` |
| 知識（結） | `local/<所属>/知識.yui` |
| 指示（その所属の決めごと） | `local/<所属>/指示.md` |
| 環境変数（認証の切り替え） | `local/<所属>/settings.json` の `env`（例: `GH_CONFIG_DIR`、`GIT_CONFIG_GLOBAL`） |
| セッション名の頭 | `<所属>-<役割>`（例: `jisha-main`） |

- セッションを起こすとき、紡は**その所属のものだけ**を渡す（`--settings`、`--add-dir`、
  `--append-system-prompt-file`）。
- 所属をまたぐ `SendMessage` は**決めごとで禁止**する。★同じマシンのセッションは技術的には
  互いに送れてしまうので、決めごとだけでは防げない（7 節）。

## 5. 常駐（紡のデーモン）

紡のデーモンがやることは 1 つ: **望む状態と実際を突き合わせて、差を埋める。**

```
望む状態:  local/*/所属.json   … この所属で、この名前のセッションを、この指示で 1 本
実際:      claude agents --json
差:        足りない → claude --bg で起こす / 余計 → claude stop / 落ちた → 起こし直す
```

- 一定間隔で回す。何度回しても結果が同じになるように作る。
- OS への登録は紡が受け持つ:

| OS | 登録先 |
|---|---|
| Linux | systemd のユーザーユニット（`systemctl --user`） |
| macOS | launchd の LaunchAgent |
| Windows | タスク スケジューラ（ログオン時に起動） |

コマンドの案:

```
tsumugi run         前で回す（デバッグ用）
tsumugi install     OS に登録する / uninstall で外す
tsumugi status      所属ごとに、望む状態と実際を並べて出す
```

## 6. 知識（結）

- 知識は**所属ごとの `知識.yui` に入れる。** セッションは結の CLI で引く・書く。
- ★**Claude Code の自動メモリには頼らない。** 端末やクライアントが変わっても、
  同じ所属なら同じ知識が引けるようにするため。止め方は、所属の `settings.json` に
  `"autoMemoryEnabled": false`（または環境変数 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`）。
  これでフックと `CLAUDE.md` の読み込みが残るかは公式の文書に書かれていないので、実測して確かめる。
- 結のファイルは公開リポジトリに入れない（`.gitignore` で `*.yui` を弾いている）。

## 8. 前身からの引き継ぎ

前身（非公開・tmux 前提・他の AI 製品でも動くことを狙っていた）の道具は、こう置き換える。

| 前身 | 紡では |
|---|---|
| セッションを起こす道具 | `claude --bg` を所属の設定つきで呼ぶ（5 節） |
| 艦隊の一覧・台帳 | `claude agents --json` ＋ 所属の設定 |
| 死活監視（cron） | 紡のデーモンの突き合わせ（5 節） |
| セッションに話しかける道具 | `SendMessage` |
| 止める道具 | `claude stop` |
| Windows への橋渡し | 不要（Windows でも Claude Code を直接動かす） |
| 編集を自動で push するフック | 所属ごとの設定で持つ（未設計） |
